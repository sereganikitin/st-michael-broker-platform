# Надёжность фиксаций и сверка уникальности

Локальная доработка от 17.11.2026. Основа: `8086d9aa8a50f92360014366ef71e6fc2712f9d6`, ветка `fix/amo-uniqueness-followup`. Изменения не развёрнуты. Производственные данные, CRM и сервер не использовались для проверки.

## Проблема и границы диагноза

В прежнем пути любая ошибка обработки переводила защиту от повторной отправки в неопределённое состояние на 10 минут. Это происходило и при отказе проверки до создания сделки; сообщение при этом предлагало повторить через минуту. Вебхук мог завершиться успешно после неудачного чтения сделки. Периодическая сверка уникальности отсутствовала. Закрытие нового КЦ-лида пропускалось при отсутствии связи брокера с amoCRM. Снятие исключения по одному телефону могло затронуть другую фиксацию.

В разобранном случае сделку создали вручную после неудачной передачи из кабинета. Первоначальная причина отказа и связь этой ручной сделки с записью кабинета не подтверждены. Доработка не угадывает такие связи по ФИО или телефону и не исправляет исторические карточки автоматически. Имена клиентов и идентификаторы реальных сделок в публичный отчёт не включены.

## Новый путь заявки

1. `POST /clients/fix` проверяет формат и сохраняет заявку в PostgreSQL. Ответ означает принятие заявки, а не подтверждение уникальности или создания сделки.
2. Форма сохраняет UUID отправки в браузере под хешем данных и ID пользователя. Перезагрузка и потерянный ответ сохраняют тот же UUID. Содержимое формы не записывается в localStorage. Явная новая фиксация сбрасывает UUID.
3. Таблица `fixation_request_keys` хранит постоянную связь `(actor_id, key)` с заявкой. Для одновременно активных одинаковых заявок из разных вкладок сохраняются дополнительные ключи. Повтор завершённой заявки с прежним ключом возвращает прежнюю заявку; новый ключ после завершения допускает новую фиксацию.
4. Обработчик каждые 30 секунд выбирает до пяти заявок. Захват выполняется атомарным `updateMany`; аренда на 10 минут продлевается каждые 30 секунд. Транзакция приёма использует advisory lock только на время записи в БД, без запросов в CRM.
5. До изменения Client/сделки фиксируется переход `CHECKING → MUTATING`. Временные ошибки проверки повторяются с задержкой, максимум шесть попыток. Неизвестный этап, неоднозначные контакты и другие неподтверждённые ошибки направляются сотруднику.
6. После возможного создания сделки повторный вызов `fixClient` запрещён. Неопределённый результат остаётся на сверке. Имеющийся механизм восстановления передачи по маркерам `AMO_CREATE_*` сохраняется; новая очередь не снимает эти маркеры и не повторяет POST вслепую.
7. Перезапуск возвращает просроченный `CHECKING` в проверку, а `MUTATING` — на сверку. Подтверждённая связь `fixationRequestId → Client → amoLeadId` завершает ожидание передачи.

| Состояние | Отображение и действие |
| --- | --- |
| `PENDING`, `PROCESSING` | Заявка принята / проверяется. Повторная подача не нужна. |
| `RETRY` | Временная задержка, проверка повторится автоматически. |
| `DELIVERY_PENDING` | Запись сохранена, передача в amoCRM не подтверждена. Включает `amoSyncStatus=PENDING` и `FAILED`. |
| `NEEDS_REVIEW` | Требуется сотрудник. Ошибка хранится в виде кода без текста исключения. |
| `COMPLETED` | Показывается текущая уникальность связанного Client, включая последующие изменения из вебхуков. |

Брокер видит только свои заявки: до 50 активных, затем 20 последних завершённых. MANAGER/ADMIN видят на странице клиентов до 50 старейших заявок, требующих сверки, и диагностический код. Кнопка повтора доступна только для `NEEDS_REVIEW + CHECKING`; действие записывается в аудит. Для `MUTATING` эта кнопка отсутствует, сервер также запрещает повтор.

## Уникальность и задача менеджеру

- Очередь `amo-uniqueness` повторяет чтение и обработку после сбоя вебхука: до восьми попыток с увеличением задержки. Неудачные задания сохраняются в Bull, до 1000 записей.
- Сверка каждые 10 минут выбирает по 50 связанных клиентов в `UNDER_REVIEW` и `CONDITIONALLY_UNIQUE`, с раздельными постоянными курсорами. Время полного обхода зависит от числа клиентов и состояния очереди. Исторические записи и оплаченные сделки исключены из выборки.
- КЦ-лид, закрытый в 143, отклоняет только связанные с ним фиксации, в том числе без amoContactId брокера. Защита оплаченных сделок сохраняется.
- Исключение `EXCEPTION_AFTER_SALES_MEETING:<id>` снимается по точному исходному sales-лиду либо разрешённому этапу нового КЦ-лида. Перед снятием проверяется состояние нового лида и прикрепление брокера. Закрытие другого КЦ-лида с тем же телефоном не снимает исключение.
- Для исключения после встречи создаётся задача с двумя ссылками и постоянным маркером. Ответственный — человек, назначенный на лид, либо ответственный актуальной открытой задачи, если лид ещё принадлежит системному пользователю.
- Перед созданием задачи читается полный список задач, включая завершённые, в пределах заданного лимита. Неполный ответ не считается отсутствием задачи. Перед POST сохраняется уникальная запись `AMO_REVIEW_TASK_V1:* = armed`; после подтверждения — `confirmed`. Потерянный ответ сверяется только чтением. Не найденная после неопределённого POST задача требует проверки сотрудником; автоматического повторного POST нет.

## Миграция и проверка перед внедрением

Миграция: `packages/database/prisma/migrations/20261117000100_durable_fixation_requests/migration.sql`. Добавляет таблицы заявок и ключей, а также nullable unique `clients.fixation_request_id`. Существующие записи не переписывает. Схема Prisma проверена, локальный клиент сгенерирован. На локальной PostgreSQL 16 успешно применились все 33 миграции с нуля. Отдельно проверено обновление базы с заранее созданным клиентом: прежние поля, amoLeadId и уникальность сохранились; новая связь nullable, ограничения уникальности и внешние ключи работают. Повторный `migrate deploy` не нашёл неприменённых миграций.

Перед внедрением остаётся проверить реальные ответы, вебхуки, поля и этапы на отдельном тестовом аккаунте amoCRM, а также полное развёртывание в тестовом окружении. Только после этого согласовывать production-развёртывание. API и веб следует выпускать согласованно: контракт POST теперь асинхронный. Не возвращаться к старому синхронному обработчику с незавершённой очередью без отдельного плана.

Первый набор локальных проверок использует заглушки CRM, Redis и Prisma и не запускает приложение с его фоновыми заданиями. Проверены двойная отправка, алиас вкладки, потерянный ответ записи, перезапуск, конкуренция обработчиков, предел повторов, текущий статус после вебхука, запрет повторного POST после неопределённого результата, права на очередь, повтор и потеря вебхука, задача и потеря её ответа.

Результат первого прогона: 244 серверных теста в 10 наборах и 2 теста браузерного идентификатора прошли. Проверки типов API и web завершились с кодом 0; `prisma validate` подтвердил корректность схемы.

## Дополнительные локальные испытания, 17.11.2026

Стенд: отдельные PostgreSQL 16 и Redis 7 из `docker/compose.fixation-test.yml`, HTTP-имитатор CRM на loopback, реальные сервисы фиксации, журнал заявок, Redis lease, Bull, контроллер и JWT/роли. Обращений к внешним адресам не было. `AppModule` и общие production-планировщики не запускались. CRM-проверка и формирование лида заменены локальными сценариями; связь брокера с CRM задана синтетически. Поэтому испытание не подтверждает соответствие конфигурации настоящего amoCRM.

Прошли 12 интеграционных сценариев:

1. Полная цепочка миграций, индексы и внешние ключи.
2. HTTP-проверка авторизации и запрета доступа брокера к очереди сотрудников.
3. 20 одновременных отправок и 8 обработчиков: одна заявка, один Client, один POST сделки.
4. 12 конкурирующих ключей вкладок: постоянная связь с одной заявкой, включая новый экземпляр обработчика.
5. Временный отказ CRM до создания сделки: сохранение заявки, повтор и успешная передача после восстановления.
6. Потеря HTTP-ответа после принятия POST сделки: сохранение маркера, отсутствие повторного POST и запрет ручного повтора проверки после начала создания.
7. Принудительная остановка отдельного процесса во время CHECKING: после истечения аренды заявка выполняется один раз.
8. Принудительная остановка после принятия сделки: повторного POST нет; после подтверждённой связи с известной тестовой сделкой заявка завершается. Истечение 10-минутных аренд имитировалось изменением срока только этих тестовых записей.
9. Конкуренция при создании задачи и потерянный ответ: одна задача, подтверждение через GET, повторный вебхук не создаёт новую задачу.
10. Пропущенный вебхук: периодическая выборка и настоящий обработчик Bull обновляют статус.
11. Остановка контейнера Redis: приём заявки сохраняется, обработка ждёт, после восстановления создаётся одна сделка.
12. Остановка контейнера PostgreSQL: CRM не вызывается; после восстановления повтор сохраняет одну заявку.

Дополнительно прошли 5 проверок миграции на заполненной отдельной базе и 5 сценариев в headless Chrome: потерянный ответ с перезагрузкой, переход от принятой заявки к результату, обновление результата после закрытия сделки, двойное нажатие, недоступное хранилище браузера. В браузере использованы исходные `FixationPage` и `FixationRequests` с настоящим локальным HTTP API; оболочка Next/navigation и контекст авторизации изолированы. Полная сборка и запуск Next-приложения этим не проверялись.

Новых дефектов продуктового кода в этих испытаниях не выявлено. Проверка типов тестового стенда также прошла. Отчёты последнего прогона сохраняются в `tmp/fixation-local/results.json`, `migration-upgrade.json`, `browser-results.json`; снимок результата — `browser-current-status.png`. ### Повторение интеграционного прогона

Команды выполняются из корня отдельной рабочей копии. Скрипты используют только выделенную базу `127.0.0.1:55441/fixation_local_test` и Redis `127.0.0.1:56381`. Интеграционный прогон очищает синтетические данные именно этой базы; не запускать два прогона одновременно. Испытания остановки сервисов затрагивают только контейнеры указанного compose-проекта.

```powershell
docker compose -f docker/compose.fixation-test.yml up -d --wait --pull never
$env:DATABASE_URL = 'postgresql://fixation_test:local-test-only@127.0.0.1:55441/fixation_local_test'
node node_modules/prisma/build/index.js migrate deploy --schema packages/database/prisma/schema.prisma
$env:TS_NODE_PROJECT = 'apps/api/tsconfig.json'
$env:AMO_BG_MIN_GAP_MS = '0'
$env:AMO_BG_HOLD_AFTER_INTERACTIVE_MS = '0'
node -r ts-node/register/transpile-only apps/api/test/fixation-local/run.ts
node scripts/test-fixation-migration.cjs
```

Для браузерного прогона запустить тот же `run.ts --serve` в отдельном терминале. Он создаёт новый синтетический набор и не запускает серверные сценарии повторно. Собрать CSS из `apps/web` командой `node ../../node_modules/tailwindcss/lib/cli.js -i src/app/globals.css -c tailwind.config.js -o ../../tmp/fixation-local/style.css`. Затем из корня запустить `node scripts/test-fixation-browser.cjs`. Требуются установленный Chrome и Playwright; переменная `LOCAL_PLAYWRIGHT_MODULE` позволяет указать путь к уже установленному модулю без скачивания. Остановить тестовый API через Ctrl+C и контейнеры командой `docker compose -f docker/compose.fixation-test.yml stop`. Тестовые тома сохраняются для разбора.

Доработка сохраняет заявку при временной недоступности CRM, но не устраняет саму недоступность или ошибки настройки этапов.
