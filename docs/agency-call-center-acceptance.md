# Агентства v1/2: реализация для проверки

Актуальная повторная проверка 27.10: см. `agency-call-center-audit-20261027.md`.

Статус: локальный первый рабочий цикл и панель контроля. Не production-релиз,
не запуск пилота и не подтверждение готовности всего проекта из PDF.

## Что реализовано

- `/admin/agencies-v1-2/workspace`: короткая очередь, поиск, представления
  «Сегодня», «Просрочено», «Новые», «Перезвонить», «Без телефона».
- Одна карточка по `Agency.id`; исторические периоды Google внутри карточки.
  Неоднозначные и новые строки не создают сущности. Ранее назначенная работа
  остаётся видна, даже если следующий снимок потерял сопоставление.
- Проверенные контактные лица: основной/запасной телефон, должность, источник,
  дата проверки, архивирование, версия и история изменений.
- Отдельно утверждаемый скрипт с владельцем и сроком; истёкший текст не
  предлагается как действующее условие. Сроки повторов не вычисляются догадками.
- Сохранение результата через существующий `LoyaltyCallAttempt`, уникальный
  `submissionId`, версию назначения и транзакцию. Журнал и исправления сохраняют
  оригинал; исправление обязательства синхронизирует ещё открытый следующий шаг.
- Следующий шаг через `LoyaltyTask`, точное время с часовым поясом,
  ответственный — назначенный оператор. Повторный звонок запускается явно из
  открытой задачи; исходная попытка и связь задачи с ней сохраняются.
- Запрет звонков на Agency, отмена открытых назначений, проверка запрета при
  назначении и записи результата; снятие руководителем с причиной и аудитом.
- Подготовка пилота через существующие кампании: только сопоставленные ID,
  только с актуальным скриптом, атомарное создание черновика и назначений,
  квитанция идемпотентности. Активировать кампанию нужно отдельно.
- Переназначение с версией и передачей открытых задач; уникальный частичный
  индекс не допускает два открытых назначения одному агентству.
- Перед звонком карточка закрепляется за сеансом. Хэш сеанса хранится на
  сервере, исходный идентификатор не возвращается в списке; сохранение из
  другого сеанса блокируется. Web Locks предотвращает работу второй вкладки
  того же браузера. Занятость снимается завершением или переназначением;
  автоматического срока, способного разрешить параллельный долгий звонок, нет.
- Контроль: период МСК, фильтр сотрудника/кампании, отдельные числа уникальных
  агентств и попыток, открытые просрочки, раскрытие до событий, CSV,
  личные фильтры браузера и переиспользованные сохранённые представления
  руководителя. Права проверяются сервером.

## Источники и пределы

Рабочее место читает только сохранённый проверенный снимок. Открытие страницы
не обращается к Google. При инциденте синхронизации или старом снимке выводится
предупреждение. Действующий импорт 10/15/20 МСК, тихие уведомления и fallback
не менялись. Вкладки «Контакты»/«Обзвон БТ» не добавлялись к импорту.

Суммы показаны только внутри исходных периодов и не прибавляются к amoCRM.
Разговоры в панели — классификация оператора, не подтверждённое соединение
Mango. Подтверждённые сделки/реактивации и оценка качества не выводятся как
достоверные факты. Телефония, записи разговоров, массовые отправки не запускались.

## Расчёт показателей

- Назначено: уникальные Agency.id с назначениями до конца выбранного периода
  в выбранной кампании/команде. Это размер назначенной базы, не число попыток.
- Попытки: исходные строки CallAttempt по occurredAt в полуоткрытом периоде
  `[начало, конец)`. Строки исправлений не добавляют попытку.
- Агентства с попыткой: уникальные Agency.id исходных попыток периода.
- Разговор: актуальный результат оператора из набора CALLBACK,
  SEND_INFORMATION, BROKER_TOUR_SCHEDULED, AGREEMENTS_EXIST,
  COOPERATION_AGREED, COOPERATION_DECLINED, DO_NOT_CALL.
  Исправления относятся к дате первоначальной попытки.
- Договорённости: актуальные результаты BROKER_TOUR_SCHEDULED,
  AGREEMENTS_EXIST, COOPERATION_AGREED с записанным шагом и временем.
- В срок: выполненные задачи с completedAt <= dueAt среди задач со сроком в
  периоде. Отменённые и без срока исключены. Просрочка — открытые задачи с
  dueAt < сейчас, независимо от выбранного периода.
- CSV содержит исходные попытки и их исправления с отдельными датами события
  и исходной попытки, признаком актуальной версии; исправление не считать ещё
  одним звонком. При отсутствии событий это ноль записанных событий кабинета,
  не доказательство отсутствия внешних звонков.

## Проверка перед применением

Миграция `20261026120000_agency_call_control` добавляет только операционные
поля Agency и частичный уникальный индекс открытых назначений. Если уже есть
дубли, она должна завершиться ошибкой и откатиться целиком. Сначала отдельно
проверить и вручную разрешить такие дубли; миграция их не удаляет.

Команды локальной проверки (без подключения к production):

```text
node node_modules/typescript/bin/tsc --noEmit --incremental false -p apps/api/tsconfig.build.json
node node_modules/typescript/bin/tsc --noEmit --incremental false -p apps/web/tsconfig.json
cd apps/api
node ../../node_modules/jest/bin/jest.js --runInBand agency-workspace.service.spec.ts loyalty-workflow.service.spec.ts loyalty-permission.service.spec.ts partner-sheet.spec.ts loyalty-workflows.migration.spec.ts
cd ../..
node --test scripts/partner-sheet/*.test.cjs
cd apps/web
node --import tsx --test src/lib/loyalty-base-api.test.ts
```

`scripts/test-agency-call-migration.cjs` использует PGlite (PostgreSQL WASM) в
памяти. `PGLITE_MODULE` задаёт установленный модуль. Он проверяет DDL, уникальный
индекс, повтор после завершения, отсутствие влияния на брокеров и откат при
старых дублях. Это не многопроцессный нагрузочный тест production PostgreSQL.

`scripts/test-agency-workspace-ui.cjs` использует Playwright и локальный Next
dev server. Все API-запросы перехвачены, данные искусственные; внешние запросы
блокируются. `PLAYWRIGHT_MODULE`, `CHROME_PATH`, `AGENCY_UI_URL` задают окружение.
Проверяет повтор после сетевого сбоя, сохранение черновика/истории, группировку
периодов, отсутствие телефона и отсутствие горизонтального переполнения.

## Решения и приёмка перед запуском

1. Подтвердить запись новых действий в кабинете и набор результатов.
2. Назначить владельца скрипта, утвердить актуальные условия и срок.
3. Назвать двух операторов и ограниченную выборку агентств пилота.
4. Утвердить полномочия READ_OWN_QUEUE/CALL_EXECUTE/ENTITY_EDIT для операторов;
   READ_ALL/CALL_ASSIGN для руководителя; отдельно REFERENCE_MANAGE и EXPORT.
   Проверить на реальных тестовых учётных записях, не расширяя доступ всем.
5. Утвердить сроки/типы повторных действий. Теперь действие имеет тип CALL / SEND_MATERIALS / MEETING / OTHER и явный текст задачи; время вводится вручную. Автоматические SLA не задавались. Формулировки и справочник можно согласовать до расширения.
6. В staging с отдельной БД выполнить миграцию, генерацию Prisma, проверить
   два параллельных сеанса, переназначение во время открытой карточки,
   исправление, запрет/снятие запрета, потерю сопоставления при новом снимке.
   Локальный браузерный тест использует mock API, не заменяет эту проверку.
7. Отдельно согласовать публикацию, production-миграцию и запуск пилота.
   Видимость репозитория, fork-связи, ключи и настройки доступа не менялись.

При потере сеанса руководитель проверяет отсутствие текущего разговора и
переназначает карточку, при необходимости тому же оператору. При перезагрузке
той же вкладки оператор повторно нажимает «Взять в работу»: идентификатор
в sessionStorage позволяет подтвердить свой сеанс. До подключения телефонии
нужен staging-прогон двух реальных сеансов и согласованный порядок восстановления.

## Выполненные локальные проверки

- API: 98 тестов, 5 наборов, без ошибок.
- Чтение/идентичность/периоды исходной таблицы: 42 теста, без ошибок.
- Контракты frontend: 68 тестов, без ошибок.
- TypeScript API build config и web: без ошибок.
- Prisma schema validate: успешно, с фиктивным URL без подключения к БД.
- SQL-миграция в PGlite: успешно, включая откат на дублях.
- Playwright: успешно на искусственных данных, в том числе блокировка второй
  вкладки, повтор после обрыва сети с тем же submissionId, перезагрузка истории,
  группировка периодов и мобильная ширина.

Снимки интерфейса сделаны на искусственных данных. По состоянию на 26.10 полный production build и реальная миграция ещё не выполнялись. 27.10 выполнены оба production build, миграции на настоящем локальном PostgreSQL и браузерные проверки с реальным API; подробности в повторном аудите. Production-пилот не запускался.
